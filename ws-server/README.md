# ws-server

Node-сервис на `ws` + `y-websocket`: WebSocket-сервер для совместного редактирования Space (Yjs CRDT). Один процесс, in-memory состояние документов — обслуживает только realtime-синхронизацию, всё остальное (авторизация, персистентность содержимого Space в БД, REST) остаётся на стороне основного Next.js-сайта.

Как это соотносится с бизнес-логикой Space — [`../docs/business_logic.md`](../docs/business_logic.md); список вызовов и поведение при недоступности сервиса — [`../docs/integrations.md`](../docs/integrations.md).

## Протокол (по факту чтения `server.js`)

1. Клиент сначала получает одноразовый JWT у самого Next.js-сайта: `GET /api/space/[id]/ws-token` (см. клиентский хук `src/app/[locale]/space/[spaceId]/hooks/useYjsSpace.ts`, коротко — он же выбирает адрес сервера через `NEXT_PUBLIC_WS_URL`, по умолчанию `ws://localhost:3035`).
2. Клиент открывает WebSocket через `y-websocket`'ный `WebsocketProvider` на `${NEXT_PUBLIC_WS_URL}/space/<spaceId>?token=<jwt>`, с именем документа `space-<spaceId>`.
3. `ws-server` при подключении:
   - берёт `token` из query-строки, обязателен — без него `ws.close(4001, 'Missing token')`;
   - проверяет подпись через `jwt.verify(token, JWT_SECRET)` — при ошибке `ws.close(4001, 'Invalid or expired token')`;
   - вытаскивает `spaceId` из пути (`/space/<spaceId>`) и сверяет с `payload.spaceId` — при несовпадении `ws.close(4003, 'Forbidden')`;
   - сохраняет `payload.userId`/`payload.role` на объекте сокета (задел под presence, в коде помечено как "Wave 4" — на момент аудита presence-логики, использующей эти поля, в самом `server.js` не видно);
   - передаёт соединение в `setupWSConnection` из `y-websocket/bin/utils` с `docName: space-<spaceId>` и `gc: true` — дальше всю Yjs-синхронизацию (авары, обновления документа) делает библиотека.
4. `GET /health` — простой `200 ok` (обычный HTTP, не WS).

### Персистентность — только в памяти процесса

`setPersistence({ bindState, writeState })` в коде явно не реализована — оба хука no-op с комментарием в самом файле: `"Wave 2 will add LevelDB/Supabase persistence for cross-restart durability"`. То есть **на момент аудита содержимое совместного документа переживает переподключение клиента в рамках одного и того же запущенного процесса `ws-server`, но полностью теряется при перезапуске/передеплое контейнера** — клиенты пересинхронизируются с нуля (пустой документ), полагаясь на собственное локальное состояние Yjs-провайдера у каждого клиента, если оно у них ещё есть.

### Права на запись (viewer-роль)

В коде `server.js` роль (`ws.role`) сохраняется на сокете, но никакой проверки "viewer не может писать" на стороне сервера нет — комментарий в коде прямо говорит, что write-защита для viewer'ов сейчас **только на фронтенде** (флаг read-only в Yjs-биндинге), не на сервере. Это тот самый пункт, который стоит свериться с [`../docs/REVIEW.md`](../docs/REVIEW.md) — трактовать как известное ограничение, а не как факт наличия серверной проверки прав.

## Переменные окружения

| Переменная | Где используется | Назначение | Дефолт |
|---|---|---|---|
| `WS_JWT_SECRET` | `server.js:8` | Ключ проверки JWT токена подключения. Должен совпадать с ключом, которым сайт подписывает токен в `/api/space/[id]/ws-token`. | `'fallback-secret-key-at-least-thirty-two-chars-long'` — небезопасный, но согласованный с дефолтом на стороне сайта литерал; см. [`../docs/config_and_env.md`](../docs/config_and_env.md). |
| `WS_PORT` | `server.js:9` | Порт HTTP/WS-сервера. | `1234`; в `docker-compose.yml` явно выставлен как `1234`. |

## Сборка и запуск локально

```bash
# из директории ws-server/
npm install
WS_JWT_SECRET=dev-secret WS_PORT=1234 node server.js

# health-check
curl http://localhost:1234/health
```

Через Docker:
```bash
docker build -t ws-server .
docker run --rm -p 1234:1234 -e WS_JWT_SECRET=dev-secret ws-server
```

В `docker-compose.yml` сервис публикует порт наружу как `3035:1234` — то есть внутри сети он слушает `1234`, а с хоста/через прокси доступен на `3035` (это и есть тот порт, на который по умолчанию указывает клиентская переменная `NEXT_PUBLIC_WS_URL=ws://localhost:3035`, если она не задана).

Реальный запуск (`npm install` + `node server.js`) в рамках этого аудита не проверялся — описание по чтению `server.js`/`package.json`/`Dockerfile`.

## Ключевые файлы

- `server.js` — весь сервис: HTTP `/health`, WS-хендшейк с проверкой JWT, интеграция с `y-websocket`.
- `package.json` — зависимости: `ws`, `y-websocket`, `yjs`, `jsonwebtoken`.
- `Dockerfile` — `node:22-alpine`, `npm install --omit=dev`, встроенный `HEALTHCHECK` на `/health`.

## Известные ограничения

- **Нет персистентности между перезапусками** — весь стейт документов только в памяти процесса (см. выше, "Wave 2" ещё не реализована).
- **Запись для viewer-роли ограничивается только на клиенте**, сервер не проверяет `ws.role` при применении Yjs-обновлений — недобросовестный клиент с валидным токеном viewer'а технически может слать произвольные апдейты документа.
- **Presence (кто сейчас в комнате)** — поля `userId`/`role` на сокете сохраняются, но в `server.js` не видно кода, который их транслирует другим участникам ("Wave 4" в комментариях, на момент аудита не реализовано в этом файле).
- Дефолтный `WS_JWT_SECRET` — предсказуемый литерал; в проде обязательно должен быть переопределён и совпадать с значением на стороне сайта.
- Реальный `docker build`/`npm install` не выполнялись в рамках этого аудита.
