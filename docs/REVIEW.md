### 1. Дублирующий вебхук оплаты с отключённой проверкой подписи и без защиты от повторной обработки ✅ [ИСПРАВЛЕНО]
**Файл:** `src/app/[locale]/callback/route.ts:41-52`

Это отдельный от `src/app/api/billing/webhook/route.ts` обработчик CryptoCloud-колбэка (тот же провайдер, тот же формат данных). Ключевые отличия от «правильного» вебхука:
- При несовпадении подписи код **не прерывает обработку** — строка 47 буквально: `// Uncomment in prod if needed: return new NextResponse('Invalid signature', { status: 403 });` — это закомментированный `return`, ошибка только логируется (`console.error`), и выполнение продолжается до начисления средств.
- Если `CRYPTOCLOUD_SECRET` не задан вовсе — блок проверки подписи (строка 41: `if (CRYPTOCLOUD_SECRET && receivedSign)`) целиком пропускается, начисление происходит без какой-либо проверки.
- В файле нет ни одного обращения к модели `ProcessedPayment` — то есть **нет защиты от повторной обработки одного и того же запроса**: один и тот же POST с одним `order_id` можно отправить N раз и получить начисление N раз (`addPurchasedTokens` вызывается безусловно при валидном формате `order_id` и `status`).
- Единственная преграда — проверка формата `orderId.startsWith("UID_")` и наличие пакета по `packId` (строка 54, 63) — это не аутентификация, формат легко подделать, зная схему `UID_<userId>_..._<packId>`.

**Последствие**: при рабочем эндпоинте (даже если он сейчас не тот URL, что зарегистрирован в личном кабинете CryptoCloud) — это прямой путь к бесплатному начислению символов/отчётов на любой `user_id`, а при повторной отправке легитимного вебхука — к многократному начислению за один платёж.

**Ответ владельца**: вебхук боевой, но «старый и сырой» — не мёртвый код. **Исправлено**: раскомментирован `return` при невалидной подписи, добавлена идемпотентность через `ProcessedPayment` по образцу `/api/billing/webhook`, заодно починен баг парсинга `packId` (наивный `split('_')` ломался на именах пакетов с подчёркиванием). Проверено реальными HTTP-запросами к живой БД: 403 на неверной/отсутствующей подписи, начисление ровно один раз на валидный запрос, без повторного начисления на повтор.

### 2. `/api/tasks` проверяет сессию отдельным захардкоженным секретом — не тем, что использует вся остальная система ✅ [ИСПРАВЛЕНО]
**Файлы:** `src/app/api/tasks/route.ts:7`, `src/app/api/tasks/parse/route.ts` (тот же паттерн)

```
const JWT_SECRET = new TextEncoder().encode("super-secret-key-change-this-in-env-938210");
```

Везде в проекте сессия проверяется через `verifySession()` из `src/lib/session.ts`, который подписывает/проверяет JWT ключом из `SESSION_SECRET`. Этот роут вместо этого сам парсит куку JWT собственным захардкоженным ключом. Поскольку кука `perricheno_session` подписана `SESSION_SECRET`, а не этой строкой, — **`jwtVerify` здесь всегда будет падать на реальной пользовательской сессии**. Это одновременно:
- баг (эндпоинт задач не работает для настоящих залогиненных пользователей — либо не используется вовсе, либо есть скрытый альтернативный путь входа, не найденный при чтении этого файла),
- секрет в коде (сам факт хардкода ключа, независимо от его текущей валидности).

**Исправлено**: переключено на общий `verifySession()`. Проверено реальной подписанной сессионной кукой на живой БД: GET/POST/PUT/DELETE и `/parse` теперь работают end-to-end для настоящих пользователей (раньше всегда 401). Заодно (Фаза 2, находка №7) добавлена проверка владения — PUT/DELETE теперь скопированы на `user_id`, чужая задача даёт 404, а не тихо мутируется.

### 10a. [НОВОЕ, Фаза 3, 2026-09-03] Отсутствие защиты от отрицательного `amount` в денежных функциях
Обнаружено при написании тестов на `src/lib/db.ts` (`tests/quota-limits.test.ts`), не при чтении кода — тесты на граничные случаи (0/отрицательное/переполнение) сразу выявили структурный пробел:

- **`addPurchasedTokens(userId, type, amount)`** — `amount` напрямую идёт в Prisma `increment` без проверки знака. Отрицательное значение **молча уменьшает баланс**, при этом запись в леджер (`Transaction`) не создаётся вообще (гвард `if (amount > 0)` защищает только создание записи-леджера, не само изменение баланса) — то есть теоретическое списание денег/ресурсов без единого следа в истории транзакций пользователя.
- **`checkAndDeductUsage(userId, type, amount)`** — при отрицательном `amount` проверка `totalAvailable < amount` никогда не срабатывает (нельзя быть меньше отрицательного числа), а вычитание с отрицательным дельта фактически **возвращает** квоту пользователю вместо списания.

**Статус**: не проверял (не входило в объём этой работы) ни один реальный вызывающий код на предмет того, может ли атакующий когда-либо повлиять на знак `amount` — на сегодня все найденные вызовы передают положительные константы из захардкоженных каталогов пакетов/промокодов. Это не подтверждённая уязвимость, а структурный пробел без input-валидации в двух функциях, напрямую управляющих балансом пользователя. Тесты специально написаны так, чтобы зафиксировать факт (`[KNOWN GAP]` в названии), а не выдать желаемое за действительное. **Не исправлено** — задача Фазы 3 была написать тесты, а не чинить найденное по ходу; решение (добавить `if (amount <= 0) throw/return` в обе функции) — на усмотрение владельца.
