# Код-ревью проекта Perricheno

Дата аудита: 2026-09-02. Коммит: `244ecb7` (2026-05-19). Ветка: `main`.

Методология: построчное чтение кода (не по памяти о «типичных багах»), сверка со старым `AUDIT.md` (2026-05-04) на предмет того, что уже исправлено, `npm audit` по `package-lock.json` для реальных CVE, точечные grep-проверки (silent catch, TODO/FIXME, `any`, SQL-инъекции). Каждая находка — с файлом:строкой. Где не проверял — явно написано, домыслов нет.

**Важное уточнение по секретам**: все захардкоженные токены/пароли, найденные ниже, владелец проекта считает уже недействительными и планирует перевыпустить заново. Поэтому ниже они разбираются не как «активная утечка, шеборыш к немедленной ротации», а как **практика хардкода секретов в коде**, которую стоит исправить структурно (читать из `.env`/секрет-менеджера), — сами значения нигде в этом документе не приводятся, только файл:строка.

## 🔴 Критично

### 1. Дублирующий вебхук оплаты с отключённой проверкой подписи и без защиты от повторной обработки
**Файл:** `src/app/[locale]/callback/route.ts:41-52`

Это отдельный от `src/app/api/billing/webhook/route.ts` обработчик CryptoCloud-колбэка (тот же провайдер, тот же формат данных). Ключевые отличия от «правильного» вебхука:
- При несовпадении подписи код **не прерывает обработку** — строка 47 буквально: `// Uncomment in prod if needed: return new NextResponse('Invalid signature', { status: 403 });` — это закомментированный `return`, ошибка только логируется (`console.error`), и выполнение продолжается до начисления средств.
- Если `CRYPTOCLOUD_SECRET` не задан вовсе — блок проверки подписи (строка 41: `if (CRYPTOCLOUD_SECRET && receivedSign)`) целиком пропускается, начисление происходит без какой-либо проверки.
- В файле нет ни одного обращения к модели `ProcessedPayment` — то есть **нет защиты от повторной обработки одного и того же запроса**: один и тот же POST с одним `order_id` можно отправить N раз и получить начисление N раз (`addPurchasedTokens` вызывается безусловно при валидном формате `order_id` и `status`).
- Единственная преграда — проверка формата `orderId.startsWith("UID_")` и наличие пакета по `packId` (строка 54, 63) — это не аутентификация, формат легко подделать, зная схему `UID_<userId>_..._<packId>`.

**Последствие**: при рабочем эндпоинте (даже если он сейчас не тот URL, что зарегистрирован в личном кабинете CryptoCloud) — это прямой путь к бесплатному начислению символов/отчётов на любой `user_id`, а при повторной отправке легитимного вебхука — к многократному начислению за один платёж.

**Требует уточнения у владельца**: зарегистрирован ли этот URL (`/{locale}/callback`) как callback URL в личном кабинете CryptoCloud, или это мёртвый код от более раннего этапа разработки, который просто забыли удалить после переноса логики в `/api/billing/webhook`. В любом случае — раз эндпоинт публично доступен и рабочий, это уязвимость независимо от текущей конфигурации провайдера.

### 2. `/api/tasks` проверяет сессию отдельным захардкоженным секретом — не тем, что использует вся остальная система
**Файлы:** `src/app/api/tasks/route.ts:7`, `src/app/api/tasks/parse/route.ts` (тот же паттерн)

```
const JWT_SECRET = new TextEncoder().encode("super-secret-key-change-this-in-env-938210");
```

Везде в проекте сессия проверяется через `verifySession()` из `src/lib/session.ts`, который подписывает/проверяет JWT ключом из `SESSION_SECRET`. Этот роут вместо этого сам парсит куку JWT собственным захардкоженным ключом. Поскольку кука `perricheno_session` подписана `SESSION_SECRET`, а не этой строкой, — **`jwtVerify` здесь всегда будет падать на реальной пользовательской сессии**. Это одновременно:
- баг (эндпоинт задач не работает для настоящих залогиненных пользователей — либо не используется вовсе, либо есть скрытый альтернативный путь входа, не найденный при чтении этого файла),
- секрет в коде (сам факт хардкода ключа, независимо от его текущей валидности).

**Требует уточнения у владельца**: используется ли `/api/tasks` в проде вообще (через веб-интерфейс `/tasks` или только через `internal/bot/tasks`, у которого своя авторизация) — если основной путь входа для задач лежит через бот, этот баг может быть незамеченным месяцами.

### 3. Захардкоженные секреты в git (список, без значений)
- `get_bot_name.js:3` — токен Telegram-бота (dev-скрипт, не используется в рантайме приложения, но закоммичен).
- `src/app/api/pdf-proxy/route.ts`, `src/app/api/internal/bot/extract-text/route.ts`, `src/app/api/internal/bot/history/files/route.ts` — API-ключ Stirling PDF (везде один и тот же литерал).
- `pdf-extractor/main.go:50` — токен стороннего OCR-сервиса (PaddleOCR); этот сервис вообще не читает переменные окружения — единственный из всех, где секрет нельзя даже переопределить через `.env`.
- `docker-compose.yml:14,157-158,175-176` — пароль Postgres и MinIO задан литералом и продублирован в 3-4 местах (сам compose-файл + `.github/workflows/deploy.yml:83-87`, где `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` тоже прописаны как литералы в скрипте деплоя).
- `src/app/api/internal/bot/history/files/route.ts` — fallback-значение `PDF_API_KEY`, если переменная не задана, — само по себе строка, похожая на настоящий ключ (UUID-формат), а не безопасный дефолт вроде пустой строки.
- `src/app/api/space/[id]/ws-token/route.ts` — hardcoded fallback-секрет для подписи WS JWT, если `WS_JWT_SECRET` не задан.

Как указано в шапке документа — владелец подтвердил, что эти значения будут перевыпущены; сама проблема — что 6 разных секретов лежат в 8+ местах кода литералами вместо единого чтения из `.env` — остаётся и повторится с новыми ключами, если не изменить подход.

### 4. Уязвимость в `xlsx` (SheetJS) без официального фикса, достижима через загрузку файла пользователем
`package.json`: `"xlsx": "^0.18.5"` — прямая зависимость. `npm audit` (2026-09-02): **Prototype Pollution** ([GHSA-4r6h-8v6p-xvw6](https://github.com/advisories/GHSA-4r6h-8v6p-xvw6), CVSS 7.8) и **ReDoS** ([GHSA-5pgg-2g8v-p4x9](https://github.com/advisories/GHSA-5pgg-2g8v-p4x9), CVSS 7.5). `fixAvailable: false` — SheetJS сняли пропатченные версии с npm-реестра (публикуют их только через собственный сайт).

Библиотека реально разбирает **пользовательские загруженные файлы**, не тестовые данные: `src/app/api/r/upload/route.ts`, `src/lib/analytics/fileManager.ts`, `src/lib/analytics/pipeline/stage1_verify_data.ts`. То есть загрузка специально сформированного `.xlsx` потенциально может вызвать зависание процесса (ReDoS) или загрязнение прототипа в Node-процессе.

**Рекомендация (для Этапа 4, не делаю сейчас):** либо перейти на пропатченную сборку с сайта SheetJS (`https://cdn.sheetjs.com/...`), либо на альтернативную библиотеку (`exceljs`), либо изолировать разбор файла в отдельном процессе/контейнере с таймаутом.

### 7. Отсутствие проверки владения ресурсом
- `src/app/api/agent/scholar/search/route.ts` — проверяет, что пользователь залогинен, но не проверяет, что запрошенная `AgentSession` принадлежит именно ему (можно читать чужие scholar-сессии по id, если он известен/угадан).
- `src/app/api/tasks/route.ts` (PUT/DELETE) — обновление/удаление задачи по `id`/`taskId` без проверки, что задача принадлежит вызывающему пользователю (при условии, что баг №2 когда-нибудь будет исправлен и роут вообще заработает для реальных пользователей — тогда эта дыра станет активной).

### 8. `ws` (транзитивная зависимость `y-websocket`) — DoS, сервис публично доступен
`npm audit`: `ws@6.0.0-6.2.3` внутри `y-websocket` — memory exhaustion DoS от мелких фрагментов ([GHSA-96hv-2xvq-fx4p](https://github.com/advisories/GHSA-96hv-2xvq-fx4p), CVSS 7.5, HIGH). `y-websocket` — прямая зависимость (`package.json`), обслуживает `ws-server`, порт которого **проброшен наружу** (`docker-compose.yml:115-116`, `3035:1234`). Фикс доступен через `npm audit fix`.

### 9. Прочие некритичные, но конкретные проблемы из Этапа 2

- ~~`KASPI_MERCHANT_ID`/`KASPI_API_KEY`/`KASPI_WEBHOOK_SECRET` не доезжали через CI~~ — **[ИСПРАВЛЕНО, 2026-09-03]**: не почина́лось, а удалено — владелец подтвердил, что Kaspi Pay заброшена и не планируется; весь код и переменные убраны (`refactor(billing): remove abandoned Kaspi Pay integration code`).
- Несогласованные коды ответа (401 vs 403) для невалидного `x-bot-secret` в разных `internal/bot/*` роутах (см. `error_codes.md`).
- `LATEX_COMPILER_URL` фолбэк указывает на хост `http://latex-compiler:8000`, которого нет ни в `docker-compose.yml`, ни где-либо ещё в инфраструктуре этого репозитория.
- ~~`WS_SERVER_INTERNAL_URL` объявлена, но не читается~~ — **[ИСПРАВЛЕНО, Фаза 2, 2026-09-03]**: подтверждено grep'ом по `src/`, `telegram-bot/`, `ws-server/`, что переменная действительно нигде не читается; удалена из `docker-compose.yml`.
- `NEXT_PUBLIC_WS_URL`/`NEXT_PUBLIC_APP_URL` — публичные переменные Next.js, которые встраиваются в клиентский бандл на этапе **сборки**, но не передаются в `Dockerfile` как `--build-arg`/`ENV` на стадии `builder`. Это значит, что собранный프 клиентский бандл, вероятно, всегда содержит дефолтные значения из кода, а не то, что задано в `.env` на сервере.

### 10. Технический долг в модели данных
- `User.account_tier` и `User.plan_tier` — два поля, оба похожи на «тариф пользователя» (`prisma/schema.prisma:26,33`). Требует уточнения у владельца, чем они отличаются семантически — иначе высок риск, что часть кода читает одно поле, часть другое, и они расходятся.
- `AgentSession.status` — типизирован (`src/app/[locale]/agent/types.ts:118`) как `"generating" | "done" | "completed" | "error"` — `"done"` и `"completed"` выглядят как два значения для одного и того же состояния «готово».
- `User.referred_by` (`prisma/schema.prisma:30`) — обычное `Int?`, не `@relation` — на уровне БД это не внешний ключ, ничего не мешает записать туда несуществующий `user_id`.
- Не проиндексированы явно (`@@index` отсутствует) внешние ключи на `User` в моделях `UsageLog`, `Task`, `SystemNotification`, `LatexError`, `VisualAsset`, `Citation`, `CitationCollection` — см. `data_model.md`. Не факт, что критично при текущем объёме данных, но стоит проверить план запросов при росте таблиц.
- `/migrations/*.sql` и `/supabase/migrations/*.sql` описывают другую схему (lowercase-таблицы, RLS-политики на `auth.uid()`, характерные для Supabase Auth, которым проект не пользуется), не совпадающую с тем, что реально создаёт `schema.prisma` через `prisma db push`. Это мёртвая/устаревшая документация схемы внутри самого репозитория — риск, что кто-то (человек или ИИ-агент) применит эти SQL-файлы буквально и получит несовместимую с Prisma Client схему.

### 11. `db.ts` — «god file» с side-effect планировщиком
`src/lib/db.ts`, 666 строк — смешивает CRUD пользователей, вызовы Telegram Bot API (`sendMessage`/`editMessageText`/`deleteMessage`, строки 337, 477, 503, 524) и планировщик через `setInterval` прямо на строке 322, срабатывающий при обычном импорте модуля (side effect импорта, а не явный запуск воркера). В среде Next.js с несколькими воркерами/инстансами это может привести к повторному запуску одного и того же таймера в каждом процессе. Это же отмечалось в старом `AUDIT.md` (пункт 6-7) — не исправлено.

### 12. Качество кода — количественно
- **32** буквально пустых `catch {}` / `catch (e) {}` блока (проверено grep по `src/` и `telegram-bot/src/`; старый `AUDIT.md` указывал 76 — методология подсчёта могла отличаться, включая catch с одним лишь комментарием; за достоверную цифру беру то, что подтвердил сам).
- **281** употребление `any` (`: any`, `<any>`, `as any`) в `src/`.
- Технического долга, помеченного явно (`TODO`/`FIXME`/`HACK`), в коде почти нет — **1** совпадение на весь `src/` + `telegram-bot/src/`. Это может означать либо реально мало известных недоделок, либо что их не принято помечать комментариями (не могу проверить, какой вариант верен).

## Дополнительные находки (всплыли при написании README по папкам, Этап 1)

### 13. Мёртвый код: `AgentSessionClient.tsx` (753 строки) никогда не рендерится
**Файл:** `src/app/[locale]/agent/[sessionId]/page.tsx`

Компонент импортируется (строка 4), но сама функция страницы всегда завершается одним из четырёх `redirect(...)` (строки 14, 20, 25, 27, 29, 31) в зависимости от `doc_type` — ни одного пути, где `<AgentSessionClient />` реально возвращался бы из JSX, в файле нет. 753 строки кода компонента, соответственно, не выполняются никогда. Категория: технический долг (мёртвый код), важность — можно отложить, но при рефакторинге этой страницы стоит либо удалить компонент, либо разобраться, не должен ли он быть fallback-веткой.

### 14. `doc_type: 'literature_search'` редиректит на `/citations`, а не на `/agent/scholar/[id]`
Там же, строка 27: `if (session.doc_type === 'literature_search') redirect('/citations')`. Судя по структуре `src/app/[locale]/agent/scholar/[id]/`, для этого `doc_type` существует отдельный специализированный маршрут (`ScholarClient.tsx`), который эта ветка не использует. **Требует уточнения у владельца**: `/citations` — осознанный выбор (например, `literature_search`-сессии превратились в фичу цитат и `scholar` route используется для чего-то другого) или забытый рефакторинг маршрутизации.

### 15. Ещё одно место с захардкоженным API-ключом Stirling PDF
**Файл:** `src/app/[locale]/dashboard/actions.ts:169` — тот же ключ, что уже отмечен в п.3 (там был список из 3 файлов + Go-сервис), здесь — четвёртое место в коде с тем же литералом. Подтверждает вывод из `docs/IMPROVEMENT_PLAN.md` (п.12 по аналогии) — нужна не точечная правка, а единая точка чтения таких ключей.

### 16. Часть админ-телеметрии — заглушка на `Math.random()`
**Файл:** `src/app/[locale]/dashboard/page.tsx` — по находке агента, часть отображаемых в супер-админ-панели метрик генерируется случайно (сам код это комментирует). Не баг в проде-логике (это не влияет на пользователей), но админ, читающий эту панель как реальные метрики, будет введён в заблуждение. Категория: техдолг/вводящий в заблуждение UI, важность — можно отложить.

### 17. `dashboard/` — это не личный кабинет, а скрытая супер-админ-панель с авторизацией по одному захардкоженному `telegram_id`
Обнаружено при написании `src/app/[locale]/dashboard/README.md`. Отдельный от `User.is_admin` (используется в `/api/admin/*`) механизм — доступ к `/dashboard` проверяется сравнением с конкретным `telegram_id` в коде страницы, а не через флаг в БД. **Требует уточнения у владельца**: осознанное решение (единственный владелец, не нужна гибкость) или стоит перевести на общий `is_admin`, чтобы права доступа не зависели от значения, зашитого в код.

- **Уязвимости в toolchain Prisma CLI** (`hono`, `valibot`, `mysql2`, `deepmerge-ts`, `fast-uri`, `@prisma/dev`, `@prisma/config` и т.д. — большая часть из 23 находок `npm audit`) — это транзитивные зависимости самого `prisma`-пакета (CLI для `prisma generate`/`db push`), а не рантайм-зависимости работающего сервера (в проде выполняется только `@prisma/client` + `@prisma/adapter-pg`). Риск ограничен временем сборки/CI, не временем работы сайта. `npm audit fix --force` предложит понижение/апгрейд `prisma` — не делал этого сам, требует решения владельца (может задеть версию схемы).
- `.dockerignore` не исключает `*.db`/`*.log`/`*.txt` — раздувает **контекст сборки** Docker (не финальный образ: `Dockerfile` использует multi-stage build и в `runner`-стадию копирует только конкретные артефакты, junk-файлы туда не попадают).
- Мусорные файлы всё ещё в git: `perricheno.db`, `perricheno_real.db`, `r.pdf`, `build_error.log`, `ts_errors.txt`, `tsc_errors.log` (см. Этап 0) — без изменений с прошлого аудита.
- `SpaceInvite` не имеет `@@unique([space_id, email])` — можно наприглашать один и тот же email много раз, накопив несколько активных токенов приглашения.
- `Citation` в текущей (Prisma) схеме не имеет `@@unique([user_id, cite_key])`, хотя в «мёртвой» SQL-версии (`supabase/migrations/20260422_citations.sql`) такое ограничение было — в реальной схеме, которой пользуется код, у одного пользователя технически может быть два одинаковых `cite_key`.
- `get_bot_name.js` — одноразовый dev-скрипт с секретом внутри, не используется приложением в рантайме; кандидат на удаление или перенос секрета в `.env` даже для локального использования.
- `src/middleware.ts` использует конвенцию, которую сам Next.js 16.1.6 помечает как deprecated (проверено запуском `npm run dev`): `⚠ The "middleware" file convention is deprecated. Please use "proxy" instead.` Переименование в `proxy.ts` — несрочно, но при следующем мажорном апгрейде Next.js этот файл перестанет подхватываться автоматически.
- `src/lib/analytics/fileManager.ts:63` (`cleanupOldFiles`) падает с `ENOENT: no such file or directory, scandir 'C:\tmp\analytics-data'` при локальном запуске на Windows без предварительно созданной директории (проверено запуском `npm run dev` на этой машине) — ошибка перехватывается и не роняет процесс, но исполняется на каждом старте/интервале и засоряет логи. В проде путь существует как tmpfs-volume Docker, поэтому там не проявляется — но функция не создаёт директорию сама (`fs.mkdir(..., {recursive: true})` перед `readdir` отсутствует), что делает её хрупкой к окружению.
- Полный `npm audit` (включая devDependencies, не только `--omit=dev`) после `npm ci` показывает **32** уязвимости (1 low, 12 moderate, 19 high) — дополнительно к 23 из основного раздела выше добавляются проблемы в чисто dev-инструментах (например, тестовые/сборочные транзитивные пакеты). Не более детализировал, так как рантайма прод-сервера они не касаются (см. п. про Prisma CLI toolchain выше).
- `src/app/actions.ts:23` (по находке агента) — список моделей вида `claude-3.5-sonnet`/`gemini-2.0-flash`, похожий на неиспользуемый черновик мультимодельного чата поверх n8n — стоит уточнить у владельца, актуален ли этот код-путь, или это мёртвый эксперимент.

## Отсутствие тестов на критичную логику

Во всём репозитории (проверено через Glob по `**/*.test.*` в Этапе 0) **нет ни одного тестового файла** — ни unit, ни интеграционных, ни e2e. Это касается в том числе:

| Область | Файлы | Почему критично |
|---|---|---|
| Начисление/списание денег и квот | `src/lib/db.ts` (лимиты, `addPurchasedTokens`), оба вебхука биллинга | Прямая финансовая логика; баг = либо потеря дохода, либо бесплатные ресурсы для всех |
| Идемпотентность платежей | `ProcessedPayment`, оба вебхука | См. находку №1 — отсутствие теста на «повторный вебхук не должен начислить дважды» напрямую позволило появиться этому багу |
| Аутентификация/сессии | `src/lib/session.ts`, `src/lib/telegram-auth.ts` | Компрометация = полный доступ к чужому аккаунту |
| Промокоды | `PromoCode`/`PromoUsage`, логика в `db.ts` | Деньги/лимиты; `@@unique([promo_id, user_id])` защищает БД, но бизнес-правила начисления (сумма, `max_uses`) нигде не проверены тестами |
| Удаление пользователя (`/api/auth/delete`) | Каскадное удаление всех связанных записей | Необратимая операция — один баг в порядке каскада или в проверке личности удаляющего необратимо стирает данные |
| Права доступа в Space (роли коллабораторов) | `src/lib/space-db.ts` | Совместное редактирование чужого документа/утечка приватного проекта при ошибке в проверке роли |
