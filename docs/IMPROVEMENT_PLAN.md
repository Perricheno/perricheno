# Предложение по процессу разработки

Это **предложение на апрув**, ничего из перечисленного ниже не внедрено. Каждый пункт отвечает на конкретную находку из `docs/REVIEW.md` (Этап 3) — цель не «best practices вообще», а именно то, что не даёт повторяться уже дважды воспроизведённым классам проблем в этом конкретном проекте.

---

## Почему это нужно именно сейчас (контекст из аудита)

За ~4 месяца между старым `AUDIT.md` (2026-05-04) и этим аудитом (2026-09-02) исправлено 6 из 10 критичных находок — то есть в проекте **уже есть** рабочий процесс исправления проблем. Но одновременно появились новые проблемы того же класса:
- хардкод секретов исправили в одном месте (`telegram-auth.ts`) — появился в новых местах (`get_bot_name.js`, `pdf-extractor/main.go`, ключи Stirling PDF);
- незащищённые платёжные эндпоинты закрыли (`billing/webhook`, `telegram/send`, `canvas/generate`) — но существует второй, отдельно написанный обработчик того же платёжного колбэка (`[locale]/callback/route.ts`) с отключённой проверкой подписи и без защиты от повтора.

Это типичная картина одиночного/маленького разработческого процесса без промежуточных гейтов: багфиксы точечные, а сам процесс, который позволяет багу появиться, не меняется. Предложения ниже — про процесс, не про повторную починку того же самого руками.

---

## 1. Ввести PR-based flow вместо прямого push→прод

**Текущее состояние**: `.github/workflows/deploy.yml` триггерится на `push` в `main` и сразу деплоит на прод по SSH после одного `tsc --noEmit`. Судя по всему, промежуточного код-ревью (чужими глазами) в процессе нет — иначе не появился бы дублирующий вебхук с более слабой защитой, чем у оригинала.

**Предложение**: разработка — в ветках, слияние в `main` — только через Pull Request. `main` защищён (branch protection): нельзя запушить напрямую, обязательны прошедшие проверки из п.2 ниже. Даже при команде из одного человека PR даёт: явный diff перед мержем, место для чек-листа (п.3), место, где ADR (п.5) появляется естественно.

## 2. Расширить CI-проверки перед мержем (не только перед деплоем)

**Текущее состояние**: CI проверяет только `tsc --noEmit` для корневого Next.js-проекта. `npm run lint` существует в `package.json`, но не вызывается в CI. Go-сервисы (`r-compiler`, `python-compiler`, `research-api`, `pdf-extractor`) и `telegram-bot` (свой `tsconfig.json`) вообще не проверяются в CI — первый раз, когда сборка Go-сервиса проверяется, это `docker compose build` уже на проде внутри `deploy.sh`.

**Предложение**, добавить в CI (до мержа PR, не после):
- `npm run lint` — уже есть скрипт, просто не вызывается;
- `tsc --noEmit` для `telegram-bot/` отдельно (свой `tsconfig.json`);
- `go build ./...` (и/или `go vet`) для каждого из 4 Go-сервисов;
- `npm audit --omit=dev` (или Dependabot/Renovate, см. п.8) — 23 известные уязвимости в текущем `package-lock.json` не заметил бы никто без ручного запуска, как в этом аудите;
- секрет-сканер (`gitleaks` или `trufflehog`) на diff PR — заблокировал бы коммит с `get_bot_name.js`-подобным хардкодом ещё до мержа.

## 3. Чек-лист перед мержем (шаблон PR)

Конкретно под находки этого аудита, не общий шаблон:
- [ ] Нет захардкоженных секретов/токенов/паролей (переменные — только через `process.env`/`os.Getenv`, дефолты — не похожие на настоящие ключи).
- [ ] Если добавлен/изменён вебхук или платёжный эндпоинт — есть проверка подписи **без возможности отключить/закомментировать** и есть idempotency-проверка (по аналогии с `ProcessedPayment`).
- [ ] Если правится логика денег/квот/авторизации — добавлен хотя бы один тест (см. п.4).
- [ ] Если меняется публичный контракт API — обновлён `docs/api_reference.md` (аналогично для `business_logic.md`/`data_model.md`/`config_and_env.md` при соответствующих изменениях), чтобы не повторить ситуацию со старым `AUDIT.md`, который просто перестал отражать реальность.
- [ ] Новые файлы не добавляют бинарные/временные артефакты в git (`.db`, `.log`, `.pdf` и т.п. в корне) — см. п.11.

## 4. Обязательные тесты для денег, авторизации, необратимых операций

**Текущее состояние**: тестов нет вообще ни одного (Этап 0, подтверждено). Дублирующийся вебхук с отключённой проверкой подписи (находка №1 в REVIEW.md) — прямое следствие того, что нет ни одного теста вида «невалидная подпись → 403» или «повторный вебхук → баланс не меняется второй раз».

**Предложение** — не «100% покрытие», а обязательный минимум для конкретных зон, только по мере их изменения (не ретроактивно всё сразу):
- оба обработчика платёжных вебхуков (`billing/webhook`, `billing/kaspi-webhook`, и что бы ни стало с `[locale]/callback`) — тест на неверную подпись, тест на повторную отправку одного `order_id`;
- `src/lib/session.ts`/`src/lib/telegram-auth.ts` — тест на то, что просроченная/поддельная сессия отклоняется;
- `/api/auth/delete` — тест на каскадное удаление (хотя бы что оно вызывается с правильным `user_id`, взятым из сессии, а не из тела запроса);
- логика списания квоты в `db.ts` — тест на то, что нельзя уйти в отрицательный баланс и что порядок списания (daily → purchased, как бы он ни был устроен) соответствует `docs/business_logic.md`.

Инструмент — на усмотрение владельца (Vitest минимально инвазивен для Next.js/TS-части; для Go-сервисов — стандартный `go test`).

## 5. Лёгкие ADR для решений, которые трудно восстановить по коду

**Текущее состояние**: в проекте нет `docs/adr/` или аналога. Пример прямого следствия — непонятно (и в этом аудите помечено «требует уточнения у владельца»), является ли `[locale]/callback/route.ts` намеренным дублем на переходный период или забытым мёртвым кодом; почему `account_tier` и `plan_tier` сосуществуют; почему выбран `prisma db push` вместо версионируемых `prisma migrate`.

**Предложение**: короткий файл на решение (`docs/adr/0001-*.md`, 1 страница: контекст / решение / альтернативы / последствия) для решений, которые: (а) касаются денег/безопасности, (б) заменяют предыдущий подход, не удаляя старый код сразу. Ретроактивно стоит завести хотя бы один ADR по факту находки №1 — что использовать единственным источником правды для платёжного колбэка, а второй обработчик удалить или явно пометить deprecated.

## 6. Минимальные докстринги на сложную бизнес-логику

**Текущее состояние**: этому аудиту потребовалось три параллельных агента и несколько часов, чтобы восстановить бизнес-правила (лимиты, стадии pipeline, порядок списания) из кода — потому что почти нигде нет объясняющих комментариев уровня модуля. Это нормально для маленькой команды, которая держит контекст в голове, но плохо масштабируется и уже дало эффект «два независимых обработчика одного и того же вебхука», потому что предыдущая реализация не была явно помечена как заменённая.

**Предложение** — не требовать доксстринги на всё, а точечно: короткий (2-4 строки) комментарий в начале файла для (a) каждой стадии `src/lib/agent/pipeline/*` и `src/lib/analytics/pipeline/*` — что стадия принимает, что отдаёт, что делает при ошибке; (b) любого файла, дублирующего или заменяющего функциональность другого (с явной пометкой, какой из них актуален).

## 7. Единая практика секретов + блокировка коммитов с секретами

**Текущее состояние**: `docs/config_and_env.md` (Этап 2) — уже готовый полный список того, что должно быть в `.env`. Проблема не в отсутствии списка, а в том, что ничего не мешает разработчику (или ИИ-агенту) вписать значение литералом «для теста» и забыть.

**Предложение**: pre-commit хук (`gitleaks`/`git-secrets`) локально + тот же сканер как обязательный шаг CI (см. п.2) — единственный способ гарантированно поймать это до мержа, а не при следующем аудите через 4 месяца.

## 8. Автоматизировать проверку зависимостей

**Текущее состояние**: 23 известные уязвимости (10 moderate, 13 high) в `package-lock.json` обнаружены только потому, что в рамках этого аудита кто-то вручную запустил `npm audit`. Автоматической проверки нет.

**Предложение**: Dependabot (нативно в GitHub, минимальная настройка) или Renovate — на `package.json`/`package-lock.json` и на `go.mod`/`go.sum` всех четырёх Go-сервисов. Не обязательно авто-мержить обновления — достаточно, чтобы PR с обновлением создавался автоматически и было видно, что версия устарела.

## 9. Превратить находки ревью в отслеживаемые задачи, а не в статичный файл

**Текущее состояние**: старый `AUDIT.md` — ровно такой статичный файл. За 4 месяца часть находок исправлена, но сам файл никто не обновлял (это делает сейчас текущий аудит) — со стороны непонятно, какие 4 из 10 пунктов ещё актуальны, без построчной проверки кода заново.

**Предложение**: находки из `docs/REVIEW.md` перенести в issue-трекер (GitHub Issues, раз PAT/репозиторий на GitHub) — по одному issue на критичную/важную находку, с меткой серьёзности. Сам `docs/REVIEW.md` тогда становится снимком на дату аудита, а не единственным источником правды о том, что ещё не исправлено.

## 10. Регулярный повтор аудита

**Предложение**: не обязательно в форме такого же полного 4-часового многоагентного прогона — достаточно короткого регулярного чек-апа (раз в квартал или перед крупным релизом): `npm audit`, поиск новых хардкоженных секретов, проверка, не появился ли снова паттерн «два места делают одно и то же с разной строгостью проверки».

## 11. Гигиена `.gitignore`/`.dockerignore`

**Текущее состояние**: `perricheno.db`, `perricheno_real.db`, `r.pdf`, три лог-файла — всё ещё в git с прошлого аудита.

**Предложение**: расширить `.gitignore` (паттерны `*.db`, `*.log`, временные текстовые дампы в корне) и `.dockerignore` (те же паттерны — сейчас multi-stage `Dockerfile` спасает финальный образ, но контекст сборки всё равно раздут). Плюс пункт в чек-лист PR (п.3) — заодно удалить уже закоммиченные файлы отдельным коммитом (это не входит в этот документ — только предложение, само удаление делать не буду без отдельного запроса).

## 12. Вынести проверку подписи вебхука в общую переиспользуемую функцию

**Текущее состояние**: сейчас в проекте минимум три места, где вручную с нуля пишется HMAC/MD5-проверка подписи вебхука (`billing/webhook`, `billing/kaspi-webhook`, `[locale]/callback`) — с разным уровнем строгости в каждом. Это структурная причина, по которой находка №1 вообще стала возможна: не «забыли добавить проверку», а «проверку писали заново и на этот раз забыли доделать до конца».

**Предложение**: одна протестированная функция `verifyWebhookSignature(provider, payload, secret)` в `src/lib/`, которая либо возвращает `true`/`false`, либо кидает исключение — без опции «залогировать и продолжить». Все обработчики вебхуков вызывают её и не пишут проверку подписи руками.

---

Ничего из этого не внедряю без отдельного подтверждения — какие пункты брать в работу и в каком порядке, решать владельцу проекта.
