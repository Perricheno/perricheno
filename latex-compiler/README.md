# LaTeX Compiler Service

Микросервис на Go (Gin) для компиляции LaTeX-проектов в PDF. Новый, добавлен вместо ранее внешнего (не входившего в этот репозиторий) компилятора, на который указывали `LATEX_COMPILER_URL`/`LATEX_COMPILER_KEY` — код и настройка того сервиса нигде не хранились, терялись при каждой пересборке инфраструктуры. API-контракт этого сервиса **воспроизведён по фактическому использованию** во всех вызывающих местах (см. `docs/config_and_env.md`), а не придуман заново — существующий клиентский код (`src/app/api/agent/compile-pdf/route.ts`, `tikz/generate/route.ts`, `space/[id]/compile/route.ts`, `stage5_validate.ts`, `stage2_3_visuals.ts`, `receiptGenerator.ts`, `internal/bot/history/files/route.ts`) не менялся.

## Возможности

- Полный **TeX Live** (образ `texlive/texlive`, схема `scheme-full`) — все движки (`pdflatex`/`xelatex`/`lualatex`), `biber`, весь пакетный набор CTAN. Осознанный выбор владельца — сервис должен компилировать произвольные пользовательские документы, а не только заранее известный набор шаблонов.
- Автоматический проход `latex → [biber, если нужен] → latex → latex` для устойчивого разрешения ссылок/оглавления/библиографии.
- Выбор движка через заголовок `X-Compiler` (`xelatex`/`lualatex`; по умолчанию `pdflatex`) — обязателен для документов на казахском (`\usepackage{fontspec}` работает только под xelatex/lualatex, см. `src/lib/agent/templates/presets.ts`).
- Произвольная точка входа через `X-Main-File` (по умолчанию `main.tex`) — нужно для многофайловых проектов Space-редактора.
- Системный шрифт **Inter** установлен отдельно (`fonts-inter` из Debian) — для `\setmainfont{Inter}` под xelatex/lualatex; отдельно от CTAN-пакета `inter` (уже в составе `texlive-full`, используется `receiptGenerator.ts`'s шаблоном чека под pdflatex).

## API

### POST / (без пути — тело запроса прямо на `LATEX_COMPILER_URL`)

**Request:** `multipart/form-data`, поле `file` — zip-архив проекта (минимум `main.tex` в корне, опционально `references.bib`, `figures/*.png`/`images/*.png` и произвольные другие файлы для многофайловых проектов).

Заголовки:
| Заголовок | Обязателен | Значение |
|---|---|---|
| `x-api-key` | да | должен совпадать с `LATEX_COMPILER_KEY` |
| `X-Main-File` | нет | путь к главному `.tex`-файлу внутри архива, по умолчанию `main.tex` |
| `X-Compiler` | нет | `pdflatex` (по умолчанию) / `xelatex` / `lualatex` |

```bash
curl -X POST http://latex-compiler:8080/ \
  -H "x-api-key: $LATEX_COMPILER_KEY" \
  -F "file=@project.zip"
```

**Response, успех:** `200`, `Content-Type: application/pdf`, тело — сырые байты PDF (не base64, не zip).

**Response, ошибка:** JSON с одинаковым текстом в трёх полях `error`/`detail`/`log` (разные вызывающие места в коде сайта проверяют разные из этих полей — так контракт покрывает все сразу), обрезано до 12000 символов:
```json
{ "error": "...", "detail": "...", "log": "..." }
```
Статус ошибки — `422` для неудачной компиляции, `400` для некорректного запроса (нет файла, не найден `X-Main-File`, недопустимый `X-Compiler`), `401` при неверном/отсутствующем `x-api-key`.

### GET /health (и HEAD /health)

Без авторизации. `{ "status": "UP", "service": "latex-compiler" }`.

## Известные ограничения / решения, принятые при разработке

- **Job name всегда фиксирован** (`output`) через `-jobname=output`, независимо от имени входного файла — так итоговый PDF всегда предсказуемо лежит по пути `<workdir>/output.pdf`, не нужно парсить имя файла из `X-Main-File`.
- **`biber`, если нужен, не считается фатальной ошибкой** — если `biber` вернул ошибку, компиляция продолжается (документ может быть пригоден для чтения даже с неразрешённой библиографией); финальное решение "успех/провал" принимается только по наличию валидного `output.pdf` (`%PDF`-магический байт) после всех проходов.
- **Ограничение параллелизма** — не более 3 одновременных компиляций (буферизированный канал-семафор в `main.go`); запросы сверх лимита ждут освобождения слота в рамках собственного таймаута вызывающей стороны, не отклоняются немедленно.
- **Таймаут компиляции — 100 секунд** на весь пайплайн (`latex → biber → latex → latex`), с запасом от максимального таймаута вызывающих сторон (60–120с, см. `docs/config_and_env.md`).
- **Лимит загрузки — 100 МБ** — не следует ни из какого контракта вызывающих сторон (ни один существующий вызов не документирует ограничение), выбран как разумный дефолт.
- **Защита от zip-slip** при распаковке архива — путь каждой записи проверяется на выход за пределы рабочей директории.
- Реальный `docker build` (полный `texlive/texlive` образ — несколько гигабайт) и живая компиляция через настоящий `pdflatex`/`xelatex`/`biber` **выполнялись на сервере** (не локально — локально нет TeX Live), см. коммит, добавивший этот сервис, и `docs/config_and_env.md` для деталей проверки.

## Ключевые файлы

- `main.go` — весь сервис: Gin-роутинг, распаковка zip, запуск движков компиляции, семафор параллелизма.
- `go.mod` / `go.sum` — зависимости (`gin-gonic/gin`, `google/uuid`).
- `Dockerfile` — двухстадийная сборка (`golang:1.21-alpine` → `texlive/texlive:latest` + `fonts-inter`), встроенный `HEALTHCHECK`.

## Переменные окружения

```env
LATEX_COMPILER_KEY=<секрет>   # обязателен, сервис падает при старте без него (mustEnv, как в pdf-extractor)
```

`LATEX_COMPILER_URL` — читается вызывающей стороной (сайтом), не самим сервисом; внутри `docker-compose.yml` это фиксированный `http://latex-compiler:8080`, не секрет.
