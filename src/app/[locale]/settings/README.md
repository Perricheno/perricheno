# src/app/[locale]/settings/

## Что тут лежит

`page.tsx` (538 строк, клиентский компонент) + `loading.tsx` (скелетон загрузки). Личный кабинет пользователя, в который **встроена** мини-панель администратора — не отдельный маршрут, а условный блок внутри того же файла, видимый только если `fullUser.isAdmin` (см. `useEffect` на строке 55: `if (fullUser?.isAdmin) fetchPromos()`, и рендер-условие на строке 350).

## Зачем существует

Для обычного пользователя — просмотр профиля (аватар/имя/дата регистрации из Telegram), статистики использования (`GET /api/billing/stats`) и истории транзакций/чеков. Для пользователя с `isAdmin` (это то же самое хардкод-условие `telegram_id === '1153844209'`, что и в [`dashboard/`](../dashboard/README.md), но проверенное здесь через `fullUser.isAdmin`, приходящее из `GET /api/auth/me`) — дополнительно доступны управление промокодами (`GET/PUT /api/admin/promos`) и поиск/просмотр пользователей (`GET/PUT /api/admin/users`).

## Известные ограничения

- Смешение доменов в одном файле: обычные настройки профиля и админ-функциональность (промокоды, поиск пользователей) живут в одном 538-строчном компоненте вместо выноса админ-части в `dashboard/`, где уже есть для этого отдельная панель — не проверялось, дублируется ли между `settings/page.tsx` и `dashboard/actions.ts` логика создания промокодов, или это два независимых пути к одному и тому же.
- Авторизация административной части — тот же хардкод одного `telegram_id`, что и везде в проекте, см. [`docs/business_logic.md`](../../../../docs/business_logic.md), §9.2/§10.
- Один файл без вложенных подкомпонентов — весь UI (профиль/биллинг/промокоды/поиск пользователей) в одном компоненте.
