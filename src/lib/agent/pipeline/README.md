# src/lib/agent/pipeline/

## Что тут лежит

Реализация 6 стадий конвейера генерации отчёта плюс общий тип-контракт и обёртка над LLM-провайдером. Каждая стадия — отдельный файл с единственной экспортируемой функцией `runStageN(...)`, вызываемой по порядку из `index.ts`.

## Зачем существует

Разбиение на стадии позволяет: писать прогресс пользователю после каждого шага (`agent_sessions.stage_json`), делать `withRetry()` вокруг отдельных LLM-вызовов, а не вокруг всего конвейера, и пропускать стадии, не нужные при текущих настройках (например, весь этап references, если `useReferences=false`). Полное бизнес-описание каждой стадии, включая примеры и граничные случаи — [`../../../../docs/business_logic.md`](../../../../docs/business_logic.md), раздел 5.1 («Схема стадий»).

## Файлы (1-2 строки на файл)

| Файл | Назначение |
|---|---|
| `index.ts` (238 строк) | `runPipeline()` — оркестратор. Последовательно вызывает стадии 1→2→2.5/2.7→2.6→2.3→3→4→5, копит `totalTokens`, пишет промежуточный прогресс через переданный `writeProgress()`. Возвращает финальный `.tex`, `.bib`, статус компиляции и лог ошибок. |
| `llm.ts` (168 строк) | Тонкая обёртка над OpenAI Chat Completions (`chatCompletion`/`chatCompletionLong`). Модель захардкожена как `gpt-5-mini-2025-08-07`. Учитывает токены (картинка = 800 токенов, по прайсингу продукта), таймаут по умолчанию 90 с, класс `LlmError` с человекочитаемым сообщением при HTML-ответе от Cloudflare/шлюза. `chatCompletionLong` умеет продолжать генерацию при обрыве по `max_tokens`. |
| `types.ts` (186 строк) | Общие типы конвейера: `PipelineSettings` (все настройки генерации от пользователя), `PlanSection`, `VisualType` (14+ типов диаграмм TikZ), `ExtractedRef`, `SectionDraft`, `AssembledDoc`, `VerificationResult`, `GeneratedVisual`, `GeneratedDataFigure`. |
| `stage1_plan.ts` (269 строк) | Стадия 1 — план. Один LLM-вызов превращает промпт+настройки в структурированный outline с бюджетом слов на секцию; есть детерминированный fallback-outline по `DocType`, если модель не отвечает валидным JSON. |
| `stage2_extract.ts` (173 строки) | Стадия 2 — извлечение. Один LLM-вызов на каждый загруженный PDF (параллельно, `CONCURRENCY=4`), мультимодально (текст + встроенные картинки) → компактный JSON-конспект + BibTeX-запись. `Promise.allSettled` — один плохой PDF не валит остальные. Пропускается при `useReferences=false`. |
| `stage2_3_visuals.ts` (1018 строк, самый крупный файл в конвейере) | Стадия визуалов. LLM генерирует TikZ-код по одному из 14+ blueprint-шаблонов (mind_map, flowchart, timeline и т.д.), затем код компилируется через внешний LaTeX-компилятор **только для валидации синтаксиса** — итоговый PDF выбрасывается, сохраняется лишь исходный `tikzCode`, который стадия 4 вставляет прямо в `main.tex`. |
| `stage2_5_verify.ts` (274 строки) | Верификация: модели задаются контрольные вопросы по каждому успешно извлечённому PDF, чтобы убедиться, что контент действительно "понят" перед стадией черновика. Работает только при `useReferences=true` и наличии хотя бы одной успешной ссылки. |
| `stage2_6_r_figures.ts` (391 строка) | Данные-в-графики: если пользователь прикрепил CSV/XLSX/JSON, стадия извлекает схему (колонки/типы), планирует аналитику через LLM и генерирует R/Python-код, который реально выполняется во внешних микросервисах `r-compiler`/`python-compiler` (те же, что использует `analytics/pipeline`). Работает только при заданных `dataUploadIds`. |
| `stage2_7_enrich_doi.ts` (196 строк) | Обогащение через CrossRef API (`api.crossref.org`, без ключа) — по DOI подтягивает точные авторов/год/издание, исправляя то, что могла напутать модель на стадии извлечения. |
| `stage3_draft.ts` (330 строк) | Стадия 3 — черновик. Секции пишутся последовательно (не параллельно), каждая следующая видит краткое summary предыдущей для связности. Длинные секции используют `chatCompletionLong()` с автопродолжением. Единственное место в конвейере, подмешивающее базу знаний LaTeX (`getLatexKnowledge()` из `knowledge/loader.ts`). |
| `stage4_assemble.ts` (353 строки) | Стадия 4 — сборка. Полностью детерминированная, без LLM. Склеивает секции в единый `.tex`: нормализация UTF-8, вставка русских/казахских языковых пакетов при необходимости, сверка `\cite`-ключей с библиографией (недостающие — заглушки, чтобы `pdflatex` не падал сразу), использует `TEMPLATE_PRESETS` из `../templates/presets.ts`. |
| `stage5_validate.ts` (219 строк) | Стадия 5 — валидация. Отправляет собранный документ во внешний LaTeX-компилятор; при ошибке компиляции просит модель починить именно сломанное место и повторяет (до 2 циклов ремонта). Итог — либо скомпилированный документ, либо статус `needs_attention`. |

## Известные ограничения / технический долг

Специфичных находок код-ревью по отдельным стадиям в `docs/REVIEW.md` нет. Общие для проекта риски (281 `any`, отсутствие тестов, зависимость от внешних сервисов без явных таймаутов на каждом вызове) актуальны и для пайплайна — детали в [`../../../../docs/REVIEW.md`](../../../../docs/REVIEW.md).
